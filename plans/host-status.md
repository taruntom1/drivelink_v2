- **What exists (H3a):** `drivelink-agent` (Linux) with access, devices, routing, subscription and command-group virtualization, the per-device lease (`lease.*`: `Lease` and the `LeaseEnd` gate), exclusive operations, history (`history.*`), ClockModel events and TimePing. libdrivelink: the v2 codec (`agent.hpp`, `composeClock`), agent pings and the composed clock in `Session`, `Session::agentRequest`, `agentLeaseTake` (waits up to 15 s), `agentLeaseRelease`, `agentClients`, `listAgentDevices`. CLI: `--token`, `--device`, `--client-name`, `--lease`, `agent-devices` (with the holder), `agent-clients`. Tests: `agent_tests` (routing, groups, lease, lease end, history, config), `test_agent_wire.cpp`, `agent_integration.py` (27 scenarios, ~30 s).
- **For H3b (GUI remote mode):**
  - Lease events (`Frame{0xF0}`, `agent::decodeEvent` + `decodeLease`) are the truth about the holder: a Take that timed out on the client may still be granted later. The GUI's command group exists only while it holds the lease; a revocation (Lease event naming it as `previous_id`) means the device was disarmed and its command groups cleared by the agent.
  - History arrives right after the Hello (one or more History events, `last` = 1 on the final one), then one ClockModel event; the faults drawer's agent history decodes `decodeHistory`.
  - ARM may be answered `Busy/None` right after a handoff while an earlier holder's command group is still on the device: retry after a moment.
  - At most 16 connections per device and 8 devices per agent.
- **For H4a (ROS):** `on_activate` takes the lease with `agentLeaseTake`; `read()` gets mapped times from the Session's composed clock (the client pings the agent; nothing else to do). A revocation disarms: `read()` returns ERROR as planned.
- **Traps:**
  - **vdev serves one TCP client** and **closes its TCP link on REBOOT**, so through the agent a vdev reboot looks like device loss (Closing DeviceOffline, then back online), not a Boot event. The agent's Boot path (`Device::boot`: map reset, identity refresh, the ClockModel event after the Boot event) is covered only at unit level; a serial device keeps its port across a reboot. Check it on the bench board in H3b.
  - **Git Bash mangles `wsl --cd /mnt/...`**: run WSL commands from PowerShell (or set `MSYS_NO_PATHCONV=1`).
  - **The descriptor hash** covers `registry.yaml`, so any registry edit changes `host/test/fixtures/cli-golden.json` (`descriptor_hash`). The bench board still reports the H2e-1 hash; nothing compares it.
  - **GCC 13.1 -O3 sees paths -O0 doesn't** (H2g): a new release-only warning fails `installer`, not `host-win`.
  - **Parallel builds** in one build directory corrupt the static libraries; give subagents their own build directories.
  - **The flaky native test** (`test_configurable_loops.cpp:246`), the **host-win `motor_smoke` velocity assertion**, and rare `host-integration` timing assertions in WSL under load (`full < period` once in H3a-1; a capture flagged `irregular` in `capture_smoke` once in H3a-2, passed on rerun) still hold.
- **Open edges:**
  - The agent's Session `events` deque (4096) is never drained; bounded, only memory (H3a-1 review finding, deliberately left).
  - LIST paging with a small `max_payload` is unit-tested only (vdev reports 1024).
  - A CLI client of a device that goes offline exits 4 (timeout), not 3 (connection), as on a direct link that stops answering.
  - An ARM still in flight at a lease end, the status backstop DISARM and ARM's `Busy/None` while a Dirty command slot remains are unit-tested (the `LeaseEnd` gate) but not reproduced on vdev, which answers too fast.
  - Through an agent, `time-sync`/`time-ping` measure the agent's clock; the CLI reports whether the composed device clock is valid but maps nothing.

- **The step writes the script now** (under `firmware/test/uart_comm/` or `host/test/`) and dry-runs it against vdev or the bare board with mock modules, so the script is known to work. It runs with real modules through a flag, not a second script.
- **It adds a row here:** the step, the script and its command, the hardware it needs, what it checks and what result means pass.
- **When hardware arrives,** the step in progress pauses at a clean point and the rows for that hardware run before any further step. Otherwise they run in HW.
- **A motor script starts with the first-run procedure:** wheels off the ground, a current-limited supply, a low duty cap and a hand on the power switch.
- **A row is deleted** once it has passed, with a line in [hardware-log.md](hardware-log.md).

## Models and effort

- **Plan and build** every step in one session on **Opus 5.5 at high effort**. The session that wrote the plan writes the code; there is no implementation subagent and no model switch after the plan is approved.
- **Review.** The session reviews its own diff.
