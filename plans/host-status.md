- **Traps:**
  - **WSL runs in mirrored networking** (the user's `.wslconfig`, 2026-11-20): WSL holds the PC's LAN address on eth1, localhost forwarding still works (the `benchRemote` setup), but the GUI on the same PC cannot find or reach a WSL agent's LAN address. See [docs/bench.md](../docs/bench.md), "Finding the agent (mDNS)".
  - **vdev serves one TCP client** and closes its TCP link on REBOOT: through the agent a TCP vdev reboot is device loss. A vdev on a PTY (`--pty`) keeps its port.
  - **Git Bash mangles `wsl --cd /mnt/...`**: run WSL commands from PowerShell (or set `MSYS_NO_PATHCONV=1`); PowerShell expands `$(...)` inside a `bash -c` string, so put WSL scripts in files.
  - **The descriptor hash** covers `registry.yaml`, so any registry edit changes `host/test/fixtures/cli-golden.json` (`descriptor_hash`).
  - **GCC 13.1 -O3 sees paths -O0 doesn't** (H2g): a new release-only warning fails `installer`, not `host-win`.
  - **Parallel builds** in one build directory corrupt the static libraries; give subagents their own build directories. A test binary built while a header was mid-edit can crash from a layout mismatch: rebuild.
  - **dpkg runs maintainer scripts with a fixed PATH without `/usr/local`** (seen in H3c): a `systemctl` stand-in for container tests must be in `/usr/sbin`. `runuser` stays between a test and the agent and dies by the signal; `setpriv` execs it.
  - **`gui-backend` `firmwareUpdateAbortAndLostReboot` is timing sensitive** (seen in H3c, no GUI change): it failed twice inside the gate's `host-linux` ctest in WSL and passed alone, as a whole suite and on the next gate run. Rerun the gate before suspecting a change.
  - **Docker Desktop** is installed on the PC (`%LOCALAPPDATA%\Programs\DockerDesktop`) and stopped by default. H3c and H3d started it to run the CI container tests locally and stopped it afterwards.
  - **apt in the H3d checks:** apt-get update exits 100 on every refusal (another key, unsigned, a changed index) and does not download a size-0 `Packages`, so an empty architecture is never fetched; a local build has only 26.04 amd64, so the `noble` and arm64 paths run only in CI.
  - **ROS in Docker:** mount the checkout read-only and give colcon `--log-base` for every verb (`test-result` too) or it writes `log/` into the checkout. Images `drivelink-ros:jazzy` and `drivelink-ros:lyrical` are cached locally (rebuilt when `setup_linux.sh` changes). Start Docker Desktop for `ros-jazzy`, stop it afterwards.
  - **ros2_control:** Jazzy's URDF parser needs links and joints beside the `<ros2_control>` block; `ros2_control_node` aborts when a component fails its initial activation; after every fault it logs a harmless "state interface not in available list (multiple cleanup calls)" warning.
  - **GCC 13 at -O2 (ros-jazzy):** a false `-Wstringop-overflow` on a small vector grown by push_back then insert (fixed in `Session::Impl::begin` by reserving); the other builds are -O0 or GCC 15 and never saw it.
  - **take_lease refuse** checks the holder, then Takes: a GUI Take between the two is preempted (documented; no wire change).
  - **The flaky native test** (`test_configurable_loops.cpp:246`), the **host-win `motor_smoke` velocity assertion**, and rare `host-integration` timing assertions in WSL under load still hold.
- **Open edges:**
  - The agent's Session `events` deque (4096) is never drained; bounded, only memory (H3a-1 review finding, deliberately left). The CLI's agent event queue is the same.
  - LIST paging with a small `max_payload` is unit-tested only (vdev reports 1024).
  - A CLI client of a device that goes offline exits 4 (timeout), not 3 (connection).
  - An ARM in flight at a lease end and ARM's `Busy/None` after a handoff are unit-tested and handled in the GUI, but not reproduced on vdev, which answers too fast.
  - A GUI that loses and regains the lease within one command setup clears its leftover group at the next setup (exact match only); not reproduced.
  - mDNS: IPv4 only; no name-conflict probing (two agents with one instance name both answer); a unicast query to port 5353 on a host with several advertised interfaces may get another interface's address.

## Notes for later steps

Each note is deleted by the step that uses it.

- **H4d.** libdrivelink's `package.xml` names the package `drivelink`, the GUI's Debian name too; bloom would make it `ros-<distro>-drivelink`. H4d settles the ROS package names. The packages' CMake reads the root `VERSION` and `host/cmake/` outside their directories and FetchContent downloads Asio and mdns at configure: a bloom (offline) build needs both handled.

- **H6.** The `vX.Y.Z` tag's `release` job publishes the firmware zip, the installer and the ten `.deb` files (H3c), then `apt-publish` replaces `gh-pages` (H3d). v0.1.0 is already taken (tagged after H3d), so H6 bumps `VERSION` first. Release installers come from CI (open-source Qt); the local Qt carries an educational licence file.
- **H6.** `drivelink-cli` has an unversioned `Replaces: drivelink` (H3c) so H2g's single package upgrades in place: H2g's and H3c's builds share `0.1.0+g<sha>`, so no version bound separates them. Once a released version is out, it may become `Replaces`/`Breaks: drivelink (<< that version)`.

## Deferred hardware checks

A check that needs motors, a real IMU, the Pi or the robot doesn't block its step:

- **The step writes the script now** (under `firmware/test/uart_comm/` or `host/test/`) and dry-runs it against vdev or the bare board with mock modules, so the script is known to work. It runs with real modules through a flag, not a second script.
- **It adds a row here:** the step, the script and its command, the hardware it needs, what it checks and what result means pass.
- **When hardware arrives,** the step in progress pauses at a clean point and the rows for that hardware run before any further step. Otherwise they run in HW.
- **A motor script starts with the first-run procedure:** wheels off the ground, a current-limited supply, a low duty cap and a hand on the power switch.
- **A row is deleted** once it has passed, with a line in [hardware-log.md](hardware-log.md).

## Models and effort

- **Plan and build** every step in one session on **Opus 5.5 at high effort**. The session that wrote the plan writes the code; there is no implementation subagent and no model switch after the plan is approved.
- **Review.** The session reviews its own diff. An independent review agent on **Opus** at the step's review effort is required where the "Review" column of [host-steps.md](host-steps.md) says so (concurrency, wire or persistence, arm/disarm, command paths, lease and access), and also when another step's diff touches those paths or is large. The PR says which was done and why.
- **Hardware checks** on the bare bench board are run by the session after the review. Checks needing motors, a real IMU, the Pi or the robot are deferred (above). A check that needs only the PC or a Pi and can't be run by the session is run by the user from a script, and the step waits in `waiting on hardware`.
- **Haiku** is used only for search and read-only helper agents (finding code, reading CI logs). It never writes firmware or host code.
- **Max effort** isn't used by default. Use it only if a review on a step keeps missing problems that show up later, and log that in the decision log.
- **Changing a step's review effort.** If a step turns out harder (or easier) than its row says, change it in the same PR and log the reason.
- **Per-step exceptions** are approved by the user in the step plan and recorded here until the step merges. The usual pattern (H2e-3 to H3b-2): Opus 5.5 (high) plans, writes the contracts, integrates, fixes and reviews; Sonnet 5.5 subagents (high) build parts from written contracts, reviewed by the session. Past exceptions are in [archive/host-overhaul-done.md](archive/host-overhaul-done.md).
- **H4a exception (user-approved 2026-11-21).** Opus 5.5 (high) plans, writes the contracts (`mapping.hpp`, `harness.hpp`), the toolchain (`setup_linux.sh ros`, `ros_check.sh`, the Dockerfile, the validate checks, CI), the plugin (`system.cpp`), the docs, integrates, fixes and reviews; Sonnet 5.5 subagents (high) built from the written contracts: `mapping.cpp` with `test_mapping.cpp` (S1), `harness.cpp` with `test_integration.cpp` and, after review, the PTY harness and five more tests (S2), and `host/test/ros_state_check.py` (S3). Independent review on Opus (high), as required.
